# Turn 级用量方案

更新：2026-09-10。状态：turn 主表、汇总分项及采集实现已完成，真实日志及原生界面验收已完成，见 [验证记录](turn-usage-validation.md)。该决定替代此前“维持 response 级落库”的讨论结论。先修复 fork 和新旧格式重复，再处理历史额度重置。

## 粒度与归属

**最小业务及用量主记录单位是 turn，唯一身份为 `turn_id`。** `model` 是 turn 内的统计分项，`thread_id` 是原始归属；两者不扩充主记录的唯一键。不是 response 级，也不是以 `turn_id + model` 作为主记录身份。

同一 turn 出现在多个任务时，只采用最早原始任务中的完整 turn。正常扫描继续按文件创建时间顺序处理；更早原始来源晚到时，更新该 turn 的归属、时间和分项，不叠加两份副本。比较应基于来源任务的创建证据，不按文件修改时间决定。首次任务内部的后续请求仍持续更新该 turn，不能只保存第一次 token 快照。

目前只读核查的跨任务 turn 中，没有发现后续任务为同一 turn 带来新用量指纹。当前按约定忽略后续任务的同 turn 用量并计入重复事件数，不额外建立祖先或冲突明细表。普通的新轮次使用新的 turnId，正常计量。

## 用量主记录与分项

| 内容 | 保存方式 |
| --- | --- |
| 轮次身份 | `turn_id` 唯一；不能取得时保留未归属来源数据，不伪造 turnId |
| 归属 | 原始 `thread_id`、有证据的 `account_id`；项目仍使用任务的最新映射 |
| 时间 | 原始 turn 起止时间、首次来源的创建时间依据 |
| 汇总 | token 总量及输入／缓存／输出／推理分项、已知金额、未定价用量 |
| 统计分项 | turn 内按模型、用量日期、价格日期、Fast／长上下文计价档保存汇总分项；不以 response 建用量主记录 |
| 采集状态 | 原始来源定位、扫描进度、两种用量流各自的基线及已处理位置、覆盖／冲突依据 |

分项表达一个 turn 内的构成，不改变最小业务单位。主表为 `turn_usage`，附属分项复用 `usage`；分项不能称为不同 turn。`seen_json` 保存事件键、token 摘要及分项归属，只服务于增量去重，不作为请求明细。金额在采集时按实际调用输入量判断长上下文档位，再归并对应分项；不能将整个 turn 的累计输入与单次请求阈值比较。

按 turn 汇总会丢失逐响应的时间与输入分布。既定日期、费率档位内的求和与重算可以保留；如果以后改变统计时区或长上下文阈值，现有分项不足时需要重扫原日志。原日志已经消失时不能承诺恢复任意新粒度的准确结果。这一限制需要在正式数据结构确定时明确，不能沿用请求级结构的无损重算承诺。

## 新旧两条用量流

1. 在选定的原始任务中处理该 turn 的完整事件序列；事件只是采集输入，不逐条形成业务用量行。
2. 新格式使用 `token_usage_record` 的明确归属与用量，`response_id` 可用于采集阶段去重；按每个明确 response 的 `usage` 累加一次；`turn_token_usage` 不再与这些用量叠加。
3. 旧格式使用 `token_count`。其 `total_token_usage` 是任务累计，不能直接当作 turn 累计；需在原始来源内识别轮次边界、重复快照和累计重置，再形成 turn 的增量。不能假定它与新格式 `thread_token_usage` 使用相同基线。
4. 同一 turn 同时出现两种格式时分别维护用量流。有明确对应证据的重复报告仅计一次，新格式补充其身份与分项；不能把两条流直接相加，也不能仅因看见一条新格式事件就丢掉该 turn 中全部旧格式用量。
5. 混合格式的覆盖关系需要结合原始事件顺序、有效时间、用量分项和连续序列确认。相同 token 数或固定时间容差本身不是通用请求身份。无法证明覆盖时保留待核对状态，不包装成已完全去重的金额。

## 已发现的问题及证据

主对话对现有数据库的独立核查确认 47,776 条跨祖先任务的旧格式副本，合计 6,361,682,686 tokens；该数字是切换前诊断快照，重建验收另记。原审计将日期作为比对条件，漏掉了 fork 重写时间的场景，因此此前 fork 验收结论撤回。

侧边对话同步的单次只读事务结果：10,184 个有 turnId 的本地 turn，1,380 个跨任务；其中 1,343 个在不同任务里的完整用量多重集合一致，37 个后续任务仅包含首次任务的部分记录。47,776 条后续记录均匹配首次任务。该结果限定于当时已入库的数据，不代表所有未来格式均遵守同样规律。

主对话再次读取原文件确认双格式重复样本：

- 文件：`archived_sessions/rollout-2026-08-27T11-18-15-01a04139-b2cc-76a3-9906-0df67875f49b.jsonl`。
- turn：`01a0652a-d388-7251-8f78-2208dd7c0964`。
- 第 17829 行：`token_usage_record`，时间 `2026-09-03T02:48:42.211Z`，本次 172,044 tokens，`thread_token_usage.total_tokens` 为 172,044。
- 第 17831 行：`token_count`，仅晚 1 ms，本次各 token 分项完全一致，旧累计总量却为 419,766,598。

因此“两个事件累计总量必须相等才是同一次消耗”的假设不成立。侧边对话发现该 turn 中 11 条旧格式与 11 条新格式分别累计 2,192,350 tokens；应补充为真实混合格式验收样本，不能仅凭现有去重单测通过就认定解决。

## 实施与验收

1. 已覆盖：完整原始 turn、日期改写的 fork 副本、部分副本、原始来源晚到、原始任务持续追加、同 turn 多模型／跨日／多计价档、双格式不同累计基线、跨重启／重扫幂等及事务回滚。
2. v6 新建 `turn_usage`，移除 `usage.request_id/response_id`；后者只保留轮次汇总分项。采集时按单次输入判断档位，分项汇总后计价，不使用整轮输入判断长上下文。
3. **用户明确要求：项目尚未上线，旧历史统计直接清掉，不编写历史数据修复。** v6 事务清空旧用量、扫描游标及统计缓存和维护断点，然后从原日志重新采集；不创建备份、不修改 Codex 原始日志。价格、任务映射和其他独立缓存保留。
4. 两种格式按各自累计流处理；新格式后同轮次、相同 token 分项的旧格式报告绑定为同一事件别名，不能要求两条流累计基线相同。该规则由真实连续序列验证；不宣称可还原所有未知日志格式。
5. 更换查询时区后，分项首尾跨新日期时记为日期未知；精确重分日需重扫。价格阈值改变导致分项需再拆分时报告需重扫，不猜测费率。
6. App／CLI 明细语义为“轮次用量分项”。CLI JSON 保留整数，扫描报告的 `insertedRequests` 等历史字段表示采集事件数，不表示落库行数。
7. 真实 AIChat、全局统计及原生界面验收已完成，见 [验证记录](turn-usage-validation.md)。历史额度重置继续暂停，后续单独实施其方案。
