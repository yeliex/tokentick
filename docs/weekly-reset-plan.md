# 历史周额度重置计算方案修订

日期：2026-09-10。状态：方案草案，尚未改动采集、数据库或统计结果。当前实现存在误判，本方案用于替换相邻观测直接判重置的算法。

## 真实问题

当前 `LimitQuery.swift` 按 `(scope_key, limit_id)` 排序，以相邻观测比较截止时间和百分比。日志的 scope 是任务，API 的 scope 是账号。这会将同一账号的额度拆成多条任务时间线，且没有验证观测是否仍处在它声称的额度周期内。

本次只读快照有 147,604 条周额度观测：147,435 条未知账号、169 条有账号。现有算法返回 3,073 条自然重置、756 条待确认变化、1 条疑似提前重置。自然重置中：

- 1,803 条前后观测时间相同，哈希 ID 决定了这些记录的比较顺序。
- 2,965 条“新周期”的截止时间在该次观测时已经过去。
- 3,010 条前一观测在写入时就已过期。
- 只有 63 条通过最基本的前后时间夹住旧边界、两条观测均未过期检查；这不代表 63 次真实重置，仍需归并来源与验证账号。

原始 fork 日志样本在创建时刻批量写入历史事件，多条额度快照拥有相同时间戳，其截止时间来自之前不同的周。当前时间边界回退规则不能排除这些事件，额度历史因此受污染。本次发现的是额度观测问题，不据此推断所有 fork token 请求都重复；如需复核 token 计量，应另按请求事实验证。

另有 444 次同一截止时间下百分比下降，下一条又恢复到原值或更高。一次下降不能证明重置。上述检查是确定性异常筛查，不能将所有波动都断言为缓存错误。

## 计算对象

历史条目表达“一次周额度结束或提前恢复，以及此前观测到多少使用”，不表达“某个任务看到了百分比下降”。任务、rollout、行号是来源证据，不是额度归属。

- 明确账号：按账号、额度桶、周窗口归并 API 和日志。primary／secondary 是展示位置，不能替代时长或额度桶身份。
- 未知账号：保留原始观测，可以按额度桶、截止时间展示未归属的窗口证据，但不能仅因截止时间相同就确认是同一个账号，也不能按任务生成多次确认重置。未归属证据不计入账号重置次数。
- 只有明确的历史账号证据才能补归属，不能回填当前登录账号。
- 其他设备、fork 或同一任务文件中的副本不形成独立额度周期。没有可靠归属和周期证据时保留未知。

## 先整理观测，再形成周期

1. **保留事实来源。** 保存原始事件时间、接收或采集时间、截止时间、百分比、账号和文件定位。API 的观测时间是实际请求时间；日志事件时间可能是历史回放时间，不能自动视为额度快照产生时间。
2. **判定可用性。** 只有时间可信且 `observed_at < resets_at` 的快照能推进当前周期。过期快照、继承事件、时间被重写的回放以及同一时刻的冲突快照都保留证据，但不参与重置状态推进。过期证据可辅助核对旧窗口，不能补造它原本发生的时间。
3. **去重与冲突处理。** 同一明确账号、额度桶的相同观测归并来源。同一时刻值冲突时记录冲突，不能按哈希顺序人为形成先后关系；同一时间点至多推进一次状态。没有来源版本或有效时序证据时，不因来自 API 就覆盖时间更晚的可信日志。
4. **归并截止时间。** 对已经固定的周期，秒级差异只作为截止时间修正。初版建议最多 2 秒的非传递容差，保留原始值；不得四舍五入到整分钟，也不得连续吸附造成无限漂移。这个数值是根据当前 1 秒差异样本提出的工程规则，需由回放测试验证，不是上游协议保证。
5. **零用量等待状态。** 若百分比持续为 0，且截止时间随观测近似后移一周，只维护一个“尚未开始使用”的状态。首次正用量或服务端固定截止时间后再确定新周期，不把每次截止变化算重置。

百分比下降时不能用该点覆盖旧周期的可信尾部。需先判断它是新周期候选、迟到旧快照，还是无法区分的修正，保留原证据。

## 重置判定

| 场景 | 新规则 |
| --- | --- |
| 正常自然结束 | 同一明确归属下，旧快照有效，随后可信快照跨过旧截止时间并属于有效新窗口；旧周期结束时间取旧截止时间，记录依据为推断自然结束 |
| 只有旧窗口，之后没有新观测 | 可标记“已过预计截止时间，未观测确认”；时间过去本身不生成已确认重置 |
| 提前恢复 | 同账号、同桶在旧截止前明显下降，随后独立的新观测仍支持新阶段，并出现新窗口或零用量等待状态，形成一次“疑似提前重置” |
| 截止时间不变但持续下降 | 可以保留提前恢复候选；仍不能区分重置、额度调整或来源冲突，不能只因两次下降就确认为手动操作 |
| 单次下降后回到旧轨迹 | 不形成重置，保留冲突证据；不把同一响应的多份副本当作后续确认 |
| 截止时间后移但用量仍连续增加 | 只记录边界变化，不能推断提前重置 |
| 重置后多次 0% 且截止时间持续移动 | 旧周期最多结束一次，新周期保持等待首次使用 |
| 长时间无观测 | 仅保留有证据的前后窗口，空白期间不按七天补出多个周期；跨越多个可能周期时不强行判断具体重置原因 |

提前重置的时刻保存区间 `(最后一个旧状态观测, 第一个可信新状态观测]`，并另存后续确认时间。不能用发现时间或新截止减七天冒充实际手动重置时间。只有明确的重置操作证据才将原因确认成手动，其余保持“疑似”。

真实 API 样本：09-10 08:03:21 为 100%，原截止 09-15 09:47:30；08:08:27 为 0%，之后多次为 0 且截止时间随查询后移，最后开始产生正用量。这应形成一个提前恢复候选及一个新周期，不形成多个自然重置。此前 41% 到 100% 同时截止时间改变的片段，仅凭现有观测不能宣称中间发生重置。

## 重置前的使用量

分别保存并明确命名两个值：

- `last_used_percent` 与时间：旧周期最后一条可信、未过期观测的值。
- `peak_used_percent` 与时间：同一已归属周期内可信观测的最高值，用于核验是否存在回落或冲突，不冒充最终使用量。

实际最终使用百分比缺少终态证据时保持 NULL。不能对多个任务的百分比求和，也不能默认取所有来源的最大值当作最终值。展示重置前最后观测与边界的时间差，使陈旧观测的精度可判断。日志回放只有历史百分比、没有可信原时间时，只展示已观测值和时间未知。

周期 tokens 和金额暂不由百分比推算；只有请求具备账号、时间以及额度桶路由证据时才可按明确边界归集。当前缺少的字段不靠项目、任务或模型名猜测。

## 数据与修复方式

保留 `weekly_limit_observations` 事实表，补足能支持以上规则的采集时间、来源类别及回放／继承判定证据；明确原事件时间的可信程度。既有采集时间不可恢复时留空，不能填成本次修复时间。现有历史来源 JSON 尚不足以表达完整回放边界，需要按可用原日志补采证据。

周期结果是可重建的统计缓存。可放入专用 `weekly_limit_cycles` 表，保存账号／额度桶、周期状态、预计截止、观测起止、提前恢复时间区间、最后值和最高值及其证据 ID；未知归属与冲突证据不进入已确认周期总数。原始观测不因新算法排除就删除。

迁移仍遵守“不自动备份”。先新增可空字段及缓存，在隔离回放结果验证后，以事务发布新缓存；不在界面查询时对全部原始记录执行相邻差值推断。修复可重新运行，新增日志和乱序补采只重建受影响的时间线。源日志已删除的记录保留其现有证据和未知状态。

## 验收案例

- 两个任务加一份 API 观察同一明确账号周期，输出一次结束；未知账号不能被自动绑定。
- fork 回放跨越数周且时间集中重写，不生成同一毫秒中的多次重置。
- 新旧快照在各自观察时间已过期，不形成自然重置。
- 固定周期截止时间相差 1 秒不拆分；不能通过一串小偏差不断扩大同一周期。
- 自然结束前后完整观测、仅有前观测、跨越多周缺口分别处理。
- 100% 到 0%、随后多次 0% 截止漂移、最后正用量，只形成一次疑似提前恢复。
- 40% 到 5% 到 41% 不因中间一点而确认手动重置；同截止下持续低值仍保留原因不确定。
- 同时间戳冲突的插入顺序、回放顺序及分页方式不改变周期结果。
- 最后观测 80% 时不能显示最终使用 80%；峰值、最后值和最终值不混用。
- 迁移无备份、失败回滚、缓存重建中断后恢复，原始用量与金额不改变。
